## Key types

- `MasterKey` — 32 bytes, NOT Clone, zeroized on drop. Created from password (Argon2id) or recovery phrase.
- `FileKey` — 32 bytes, per-file via HKDF. `derive_file_key(master_key, file_id)`. `EncryptedBlob` — cipher_suite + nonce (Vec<u8>) + ciphertext (Vec<u8>).
- Owner per-file key conventions (SF-0002): `kdf::owner_file_key_for_name` tries the **string** id, then the legacy **binary** 16-byte UUID, then the read-only **upper_repair** (`UPPERCASE(id)`) convention, and reports which one won; `kdf::owner_file_key_for_content` does the same per content version from that version's first chunk frame. The shared readers (`decrypt_name_metadata`, `decrypt_file_metadata`, `decrypt_name_with_mime`) stay two-convention (string, then binary) — only the resolvers know `upper_repair`. A file is READ-ONLY if EITHER its name or ANY version reports `UpperRepair` — no rename, no new version, edits become a new file. Core never writes under it and never migrates a row.
- Item id classes (task 2275, L12): `item_id::new_foreign_item_id()` mints a foreign (**F**) id — RFC 9562 UUID **v8**, RFC 4122 variant, 122 CSPRNG bits, canonical lowercase hyphenated text; `item_id::is_foreign_item_id` / `item_id::item_class` classify, and every other canonical UUID is an owner (**O**) id. Any other text form (uppercase, braced, unhyphenated) is `InvalidInput` — never treated as an owner id. F ids are never derived: their key comes from an L8 owner envelope or an L7 child wrap that also authenticates the name; O ids never use those envelopes/wraps. `owned_keys::resolve_owned_key` returns the key, its `KeyOrigin`, the resolved name and — only for a writable row — a `WriteTarget` (id + key + chunk-format pin). `DerivedUpperRepair` rows and 2236 request rows have **no** `WriteTarget` (read-only). `item_id::NewItemId` is minted by core only; new-row sealers are `*_for_new_item`, replacements `*_for_target`. L14: `owned_keys::child_wrap_matches` compares the opened wrap key in constant time.
- `encrypt_chunk(key, plaintext)` / `decrypt_chunk(key, blob)` — generic AES-256-GCM, NO associated data (key wrap, search shards). **Not for file content** (goes through `chunk_stream`) — **and not for names, thumbnails or file notes** (purpose subkeys: `encrypt_name*`/`decrypt_file_metadata`, `encrypt_thumbnail[_for]`/`decrypt_thumbnail`, `encrypt_note[_for]`/`decrypt_note`).

## Shared folder key id (`folder_key.rs`)

`folder_key::folder_key_id(folder_key) -> [u8; 32]` = HKDF-SHA256(ikm = folder key, salt = none, info = `b"beebeeb/folder-key-id/v1"`). One-way id so a server can compare folder keys without learning them. Not secret, must NEVER be used as a key; a new derivation gets a new info string (`v2`), never a change to this one. Exports: WASM `folder_key_id(Uint8Array)`, UniFFI `folder_key_id(Vec<u8>)` — both refuse non-32-byte keys. Vector: `folder_key_id` in `test-vectors/vectors.json` under the `test_vectors_v2` drift guard.

## Streaming chunk primitive (`chunk_stream.rs`)

`ChunkEncryptor` / `ChunkDecryptor` are the ONE shared chunk encrypt/decrypt loop for every client (cli, desktop, mobile/UniFFI, web/WASM) — no client re-implements it. Generic-free; `Send`; core stays synchronous (no tokio).

- Pull (native): `ChunkEncryptor::from_reader(...)` — peak memory ≈ one chunk. Push (WASM): `for_push[_with_chunk_size]` + `push_chunk`; `ChunkDecryptor::for_push` + `push_frame` mirrors it. `file_key` derived ONCE in the constructor, `ZeroizeOnDrop`.
- **Chunk-size cap:** `MAX_CHUNK_SIZE = 256 MiB`; the `*_with_chunk_size` constructors reject anything above (hostile server-dictated size → client OOM guard).
- **`finish()` integrity guard:** requires `emitted == chunk_count` AND `running_ciphertext == file_size + 28*chunk_count`. Detects a SHRUNK source; a GROWN source is caught one level up in `file_encrypt::encrypt_file_to_chunks`, which re-stats the input after `finish()`. Silent truncation is a return-typed error on every client.
- **Wire format:** `nonce(12) || ciphertext || tag(16)`, fresh random nonce per chunk. New versions are written as **v2** (`WRITE_FORMAT`); every reader still reads v1 and v2.
- `file_encrypt::encrypt_file_to_chunks` DELEGATES to `ChunkEncryptor`; `tests/chunk_stream_parity.rs` enforces identical chunk plan + WRITE_FORMAT stream.
- The three legacy decrypt functions (`encrypt::decrypt_chunks_to_file`, `encrypt::decrypt_contiguous_to_file`, `file_encrypt::decrypt_chunks_to_file`) are disk/legacy paths, NOT superseded; ALL write to a sibling `.tmp` and `rename` onto the final path only on full success — no partial plaintext survives a failed decrypt.
- **WASM binding:** `WasmChunkEncryptor` wraps the push form (JS slices the `File`); `pushChunk` returns the full frame; `finish()` runs the integrity guard. `WasmChunkDecryptor` (or `decrypt_chunk_frame` for random access) is required for web file content, not the generic `decrypt_chunk`.

**Resumed uploads:** `resume_policy(stored, writing)` → `SessionResume::ContinueSession` ONLY for `(Some(V1Legacy), V1Legacy)`; everything else (including a record that doesn't name its format) is `RestartWithFreshSession` — never PUT into the old session again; upload from chunk 0 into a new session. A client told to restart MUST first `POST /api/v1/files/{id}/upload/abandon` (or wait out the lease, default 3600 s) and only then init again; a 409 from that init means retry abandon/wait — never fall back to the old session. Clients persist `ChunkEncryptor::format()` next to the session id.

**The one v2 continuation:** `beebeeb_transfer::background` (OS background uploads) continues its OWN v2 session: the same upload session, `version_id` and counter, from the next unstaged chunk, through `BackgroundUploadPlanner::resume_encryptor[_with_file_key]` → `ChunkEncryptor::resume_v2_from_reader_with_file_key`. It is not a writer adopting an unrelated old session, so `resume_policy` is not asked. The planner continues only when the restored state carries the whole commitment (`format` 2, `version_id`, counter), the source identity matches the file on disk and `staged_plaintext_matches` (the chained plaintext hash of every staged chunk) holds; otherwise `restore` returns `AbandonAndRestart` and the client abandons and starts again from chunk 0. A staged frame is handed to the OS (`next_transfers`) only after `to_bytes` persisted the state naming it; `restore` deletes unrecorded frame files and re-stages those indices, which therefore never reached the server, so no index ever has two valid frames there.

## Chunk format v2 — position binding (task 1908)

v1 frames had no AAD: within one file a malicious server could reorder/duplicate/drop/truncate/splice frames undetected. v2 = same frame layout, own subkey, AAD = position (STREAM; as in age/Tink):

```text
key = HKDF-SHA256(ikm = file_key, salt = none, info = "beebeeb/chunk/v2/key")
AAD = "beebeeb/chunk/v2"         16 bytes: domain tag + version
   || u32_be(len(file_id))       length prefix (injective encoding)
   || file_id                    exact bytes fed to derive_file_key (string UUID)
   || version_id                 12 bytes: the nonce of THIS upload's frame 0
   || u32_be(chunk_index)        0-based
   || u8(is_last)                1 on the final chunk only
```

- v2 frames never use the raw file key (key separation — no blob of another type opens as a v2 frame). `version_id` = frame 0's random 96-bit nonce (Guus's 1778 ruling: file VERSION id in the AAD). It is stored together with a positive monotonic counter in that version's encrypted metadata. Current reads require frame 0 to match; historical reads use the selected version's own metadata.
- No total count in the AAD — the last flag gives the same truncation guarantee. `file_id` is in the AAD although the key already binds it — defence in depth.
- **Mandatory pin:** every content reader REQUIRES `ExpectedChunkFormat` from the file's encrypted metadata via `decrypt_file_metadata[_with_key]` (refuses plaintext names; folders keep `decrypt_name_metadata`): `V2` = only v2 frames open; `Unrecorded` = frame 0 decides then LOCKS (residual: a server can still pass a no-AAD blob off as the whole file at position 0 — documented).
- **Writers record the format** with `encrypt_name_with_chunk_format` (`recorded_for(enc.format())`); rename/replace carry forward the decrypted value — never record `chunk_format: 2` on a file id with v1 history (its new versions are v2 under the kept unrecorded pin and MUST carry the version commitment), never drop a recorded 2; unknown recorded values are errors, never fallback to detection.
- **Metadata sealing (names, thumbnails, notes):** name/thumb/note subkeys (`beebeeb/name/v1`, `beebeeb/thumb/v1`, `beebeeb/note/v1`) replace raw-key sealing; readers try the subkey then the legacy raw key; clients must NOT open names/thumbnails via `decrypt_metadata`/`decrypt_chunk`. ONE rule for content, names, thumbnails: `chunk_stream::chunk_format_for_pin(pin)` then `encrypt::metadata_seal_for(format)`. Deviation from the round-3 ruling is recorded in task 1908; both switches flip in ONE gated release. Thumbnails only via `encrypt_thumbnail[_for]`; notes only via `encrypt_note[_for]`/`decrypt_note`.
- **Decrypt rules (`StreamOpener`):** frame i opens only at index i and (v2) under frame 0's version id; nothing may follow the last frame; `finish()`/EOF fails unless a v2 stream saw its last frame; zero frames is an error. Trial opens are safe (tag checked before keystream).
- **Random access:** `open_chunk(file_key, file_id, version_id, index, is_last, format, frame)` — format from the metadata pin, version_id from `ChunkDecryptor::version_id()` (or chunk 0's first 12 bytes).
- Generic no-AAD (`encrypt_chunk`/`decrypt_chunk`/`*_raw`, WASM `decrypt_chunks`) stays for key wrap, search shards, v1 content — never to SEAL a name/thumbnail/note under a per-file key.
- **Residual (decision 1912):** pre-switch legacy names/thumbnails under the same raw key as v1 content remain servable as content; old blobs cannot be retired by rewriting.

### Client adoption checklist (every client, before it ships on this core)

1. Read the content pin with `decrypt_file_metadata[_with_key]` (never `decrypt_name_metadata`, never a server field) and pass `chunk_format` to every content reader. The binding decryptors take that whole record: WASM `new WasmChunkDecryptor(masterKey, fileId, metadata)` / `fromFileKey(fileKey, fileId, metadata)`, UniFFI `ChunkDecryptorHandle::from_file` / `for_push` / `for_push_with_file_key_handle(…, metadata)`; `forVersion` / `for_version` / `for_version_with_file_key_handle` take its fields. A missing record or half a commitment is refused; a record with neither commitment field is legacy metadata, read unprotected.
2. Take the chunk format from the pin (or a decryptor that opened chunk 0), never from a server value; prefer `version_id()` over re-reading chunk 0's first 12 bytes.
3. Call `finish()` after the last frame and DISCARD all plaintext on any `Err`. The one exception is a range session ("Range reads" below): it releases `RangeOpener`-authenticated frames of one recorded version, and only its own finish verdict makes anything whole.
4. Every new version uses v2. For a file with legacy unrecorded history, `with_recorded_pin` keeps the history's compatibility pin while the new version still writes v2. If authenticated metadata cannot be read, do not upload.
5. After frame 0, record its `version_id` and the next monotonic counter together with `chunk_format: 2`; on rename carry all three fields forward. A replace writes the new commitment atomically with the new version metadata.
6. Thumbnails/notes only through `encrypt_thumbnail[_for]` / `encrypt_note[_for]` / `decrypt_note`; names only through the `decrypt_name*` / `decrypt_*_metadata` readers. Notes: write with `encrypt_note_for(file_key, text, pin)`, read with `decrypt_note` — never `encrypt_metadata`/`encryptFilename`/`encrypt_chunk` for a note.
7. Resuming: ask `resume_policy(stored_format)` and obey it; persist the encryptor's format with the session id.

**Write policy:** `WRITE_FORMAT = ChunkFormat::V2`. The server refuses v1 writes only when its
default-off refusal flag is enabled. Until then, matching readers and uploaders still have to be
deployed together; v1 remains readable for legacy versions.

## Request-row content reader (`request_content.rs`) — task 2275 §15, 2326

`RequestContentReader` owns the request row's content key `C` (a `FileKey`, zeroized on drop), bound to the row's file id and to the chunk-format pin its name authenticated. `owned_keys::resolve_request_row[_detailed]` builds it; the bindings expose it as `WasmRequestContentReader` / `RequestContentReader` and hand out no key. `C` is decrypt-only — the anonymous uploader holds it, so nothing is ever sealed under it. The owner's rename goes through `seal_request_rename` / `sealRequestRename` (the §15 string key derived from the item id), and a request row has NO note sealer because notes are not writable on it.

- `decryptor()` returns a FRESH sequential `ChunkDecryptor` at chunk 0 on every call. Retry contract: discard EVERYTHING the failed attempt produced; never splice attempt 1's prefix with attempt 2's suffix (after a replace that splices two uploads of one id). The failed cursor is not poisoned (`open_next` does not advance `next_index` on an error), but the output must still be rebuilt from frame 0.
- `openFrame` / `open_frame` is the random-access path: one frame by index, no earlier frames (reorder within a file is caught by the AAD). Its `format` and `version_id`/`versionId` must come from the resolved row and the frame, never from a server field. A V2-pinned reader refuses a v1 `format` as an invalid input (`CoreError::InvalidInput` / `CryptoError::InvalidInput` / a JS exception) before touching the frame; an Unrecorded reader opens the same frame, so the pin is what refuses it, not the key.
- Pin risk is two-sided (see `rename.rs`): pin 2 on a v1 row makes it unreadable until it is renamed again with the correct pin; pin 0 on a v2 row drops the recorded 2 and turns frame-0 detection back on, so a server can serve the uploader's old no-AAD name blob under `C` as a one-frame v1 file. Callers always pass the pin from the resolver's `RenameTarget`.
- The reader's `Debug` prints the file id and pin only; the key has no accessor, and a `compile_fail` doctest pins that.

### Folder-link handles (task 2237c)

Folder keys are random (`FileKeyHandle.generate`, OS CSPRNG), never derived from
the master key. Clients fetch permanent owner custody before minting a key.
`wrap_key` / `unwrap_key` keep keys in native handles: AES-256-GCM, no AAD,
`nonce(12) || ciphertext(48)`; unwrap rejects every plaintext length except 32.
`key_id` is core's one-way folder-key id, never the key itself.

`from_folder_link` combines the 32-byte URL fragment `K_c` and an optional
32-byte stretch with `combine_folder_link_key`. `from_folder_link_passphrase`
stretches with Argon2id v19 (256 MiB, 4 iterations, 2 lanes, 32 bytes), salt =
`SHA-256(UTF-8 token || "beebeeb-folder-link-passphrase-v1")[0..16]`, then combines.
Passphrases are NFC-normalized in core and empty strings are rejected. KDF
errors propagate; clients must never downgrade to an unprotected link. Argon2
uses a try-reserved explicit block buffer, zeroized on drop with argon2's
`zeroize` feature. Allocation failure returns a KDF error (OS process termination
cannot be caught).

L6 supersedes the original custody/owner-wrap rule. `wrap_folder_custody` /
`unwrap_folder_custody` derive a purpose key using HKDF-SHA256 (no salt, master
IKM), info = `beebeeb-folder-custody-v1` || folder-id bytes, and bind the same
bytes as AES-GCM AAD. Link owner recovery uses `beebeeb-link-owner-key-v1` ||
share-id bytes for K_c and `beebeeb-link-owner-token-v1` || share-id bytes for
token UTF-8. UniFFI takes canonical id strings as UTF-8. Never fall back to the
legacy file-key custody opener after authentication fails; an existing invite
may be opened separately for seeding only. MasterKeyHandle exposes these wraps
plus legacy `wrap_key` / `wrap_bytes` without exporting the master key.
WASM (2237b) exports the same wraps in the L7 byte style, wire = nonce(12) ||
ciphertext+tag, record id = the canonical id string as UTF-8:
`wrapFolderCustody` / `unwrapFolderCustody` (60-byte wire),
`wrapLinkOwnerKey` / `unwrapLinkOwnerKey`, `wrapLinkOwnerToken` /
`unwrapLinkOwnerToken`, and `deriveFolderLinkPassphraseStretch` (NFC + empty
refusal in core). They take the master key as 32 bytes like the other byte-key
exports; task 2254 moves them to handles. Pinned by
`beebeeb-wasm/js-tests/folder_owner_wraps.test.cjs` against vectors v10.

Unreleased vectors v10 include the original two families, an NFD-equality row,
and three purpose-wrap families. Python argon2-cffi/cryptography independently
produces all six; WebCrypto verifies the new purpose keys, AAD and ciphertext.
The core drift guard regenerates them. Owned secrets and scratch memory are
zeroized on success and error paths.

## Encrypted client metadata (`client_meta.rs`) — task 1922

Client-supplied free text (device hostname, session name/local path/remote path) is sealed under the
user's key; the server stores and returns only `bbcm1.` envelopes plus client-generated record keys.
- **Key:** one per user, `HKDF-SHA256(ikm = master, salt = none, info = "beebeeb/client-meta/v1/key")`, held as a `FileKey` and private to the module. `ClientMetaKey` is the opaque handle the bindings use; the derived key is never exported (a `FileKey` would also fit `encrypt_chunk`).
- **AAD:** `"beebeeb/client-meta/v1"` (22 bytes) `|| u32_be(36) || record_key` (lowercase hyphenated UUID) `|| u32_be(len(device_key)) || device_key` (36 bytes, or empty) `|| u8(field)`. `device_key` is empty for field 1 and required for fields 2-4; any other combination is `InvalidInput`.
- **Payload:** `u16_be(len) || UTF-8 || zeros` to `max(32, roundup(2 + len, 32))`; `len > 1024` is `InvalidInput` and `open` requires the exact padded length. Paths longer than 1024 bytes are shortened by `fit_for_seal` (last 1021 bytes on a char boundary behind `…`), never per client.
- **Envelope:** `"bbcm1." + base64url-no-pad(nonce(12) || ciphertext || tag(16))`, AES-256-GCM with a fresh `OsRng.try_fill_bytes` nonce (an RNG failure is an error, never a panic). Open matches the prefix case-sensitively, accepts at most 1452 chars, and requires 60..=1084 decoded bytes with `(len - 28) % 32 == 0`.
- **Field codes:** 1 device hostname, 2 session name, 3 session local path, 4 session remote path. Codes 5/6 stay reserved and are refused (`current_file`/`detail` are discarded from S1, never sealed).
- **Bindings:** WASM `ClientMetaKey` handle (`seal` / `open` / `openMany`; `field` is a checked `u32`, and UUID strings are parsed and re-rendered lowercase hyphenated) and UniFFI `MasterKeyHandle::seal_client_meta` / `open_client_meta` / `open_client_meta_many`. `fitForSeal` (WASM) / `fit_for_seal` (UniFFI) shorten a string before sealing. No free function takes the master key for this feature; the batch derives once and a bad row (null envelope, bad field/UUID/shape, failed open) is `ok: false` for that row only — a cleared key handle is an error for the whole call.
- **Residuals (accepted):** the server can replay an older envelope for the same record and field, or delete a field; both are display-only and a stateless viewer cannot detect them. The hostname is encrypted too, so admin/push see platform and client kind only.
- Vectors: `test-vectors/vectors.json` **version 13** carries `client_meta_device_hostname`, `client_meta_session_paths` and `client_meta_padding_buckets`, generated by the real seal path through the `cfg(test)` / `test-support` fixed-nonce seam and pinned by the `published_v2_vectors_match_core` drift guard plus the `cross_platform_vectors` consumer tests.

## Encrypted search index (`search_index.rs`)

Client-built, E2E-encrypted file-name search; the server is zero-knowledge, everything runs on-device, identically for every client. `tokenize(name)`: NFKD + accent-fold + separators + camelCase, dedup preserving order; keeps the full normalized name for substring fallback.
- `SearchIndex`: `build`, incremental `upsert`/`remove` (return the dirty bucket set), `query` (exact + prefix + substring).
- Sharding: `bucket = blake3(key)[..8] % num_shards` (`DEFAULT_NUM_SHARDS = 64`), pages ≤ 128 KB after encryption; `num_shards` fixed per index.
- Encryption: per-shard key `kdf::derive_search_index_key` (HKDF label `beebeeb-search-index-shard-v1`, distinct from the file-key label); `blob = nonce||ciphertext||tag` via `encrypt_chunk_raw`.
- Bindings: UniFFI `SearchIndexHandle` + WASM `WasmSearchIndex` (same surface); sync helper `search_sync::diff_manifest` (`searchIndexSyncPlan`). Dependency: `unicode-normalization` (NFKD). WASM constructors accept at most 64 shards (zero still normalizes to one), matching `deriveSharedFolderIndexKey` buckets 0–63.
- Wiring: WEB is wired (task 0871). Follow-ups: mobile wiring; retiring `/api/v1/index` (Guus-gated, after web + mobile both cut over); Part A recursive in-app search.

## Device link (`device_link.rs`, `beebeeb-client::devices`)

A signed-in device (the approver) gives a new device the account key. Two paths, both one-shot, both over the server's opaque relay (one message per role, a second post denies the link):

- **QR path** (core `DeviceLinkQr::parse` + `seal_for_new_device`; WASM `sealDeviceLink(masterKey, scannedQr, relayedPublic, typedCode)`; UniFFI `DeviceServiceHandle::approve_device_link(id, scanned_qr, typed_code)`): the new device shows `QR_PAYLOAD_PREFIX` (`beebeeb-link:v1:`) + unpadded base64url(session id (16) ‖ fingerprint (32)), the fingerprint being SHA-256 over a domain label and its one-time X25519 key. The approver passes the SCANNED TEXT; `parse` ignores surrounding ASCII white space and refuses anything but the prefix plus 48 bytes, and the seal refuses a relayed key whose fingerprint differs. No host passes session or fingerprint bytes, and `from_parts` is gone. **The typed code gives no protection against key substitution here**: a server that swaps the key and also fills the "QR" from its own data holds the DH secret and can try all 2^40 codes offline against the sealed blob. A camera-less approver uses the typed path.
- **Typed-code path** (SPAKE2 over Ed25519, asymmetric: new device = A, approver = B): the approver starts (`TypedCodeApprover::start(code, sid, device_name)` sends `0x02 ‖ B`); the new device answers (`NewDeviceLink::answer_typed_code` sends `0x02 ‖ A ‖ r(16) ‖ Td(32)`); the approver confirms (`confirm` checks Td, then `ConfirmedTypedApproval::seal`) and seals `Tb(32) ‖ GCM(48)`; the new device checks Tb before it opens (`TypedCodeReceiver::open`). Key schedule, lv = u32_be length prefix:

  ```text
  ADa = SHA-256("beebeeb/device-link/pake-ada/v2" || lv(sid) || lv(r) || lv(canonical device name))
  TH  = SHA-256("beebeeb/device-link/pake-transcript/v2" || lv(sid) || lv(ADa) || lv(A) || lv(B))
  k_td, k_tb, k_payload = HKDF-SHA256(salt = TH, ikm = SPAKE2 key, info = …/pake-confirm/v2/new-device | …/pake-confirm/v2/approver | …/pake-seal/v2/key)
  Td = HMAC-SHA256(k_td, TH)    Tb = HMAC-SHA256(k_tb, TH)
  payload AAD = "beebeeb/device-link/pake-seal/v2" || sid || 0x01
  ```

  ADa is in the transcript, not the SPAKE2 identities, because the approver must start before it knows `r`. A wrong code, a relay that rewrote the device name, another session or a replayed message all fail at the approver's `confirm` (`CoreError::Decryption`, client `DeviceError::ConfirmationFailed`, WASM `confirmation_failed`, UniFFI `Authentication`); the client then denies the link (best effort), so the new device sees it end, and nothing is sealed. Malformed or small-order peer elements are refused before the exchange (`InvalidInput` / `malformed_answer`).
- **Device name:** `canonical_device_name` strips control characters, the actor-name strip table, ZWNJ and ZWJ, trims, and keeps at most 64 scalars and 160 bytes; an empty result is refused; it is idempotent. The new device sends its canonical name and the approver refuses a relayed name that is not canonical, so both sides hash the same bytes.
- **Residuals:** spake2 0.4 copies the code into its own `Password` and keeps its scalars without zeroizing them; sha2, hmac and dalek temporaries are not wiped either. Core's own copies (the code, `r`, the HKDF output, the seeds) are `Zeroizing`. The window is one single-use link of five minutes, and both ends hold the account key anyway. The randomness is drawn with `try_fill_bytes` (`PreDrawnSeed` feeds spake2's `Scalar::random` 64 pre-drawn bytes), so an RNG failure is an error, not a panic.
- **Changing it:** every label above is in `label_table_tests.rs`; a change is a new `v3` label set and a coordinated release with the server relay, never an edit in place.

## Key proof (`key_proof.rs`)

`answer_challenge` is a hashed-DH oracle on the account X25519 key, by design: the server picks `server_public` and learns `HMAC(HKDF(X25519(account_private, server_public), KEY_INFO), transcript)` for a point of its choice. That is safe only while the shared secret never leaves through any other derivation: never use the account X25519 key with `KEY_INFO` elsewhere, and never return a raw DH output from it. Non-contributory (small-order) points are refused. The challenge side's private key is `Zeroizing` from the RNG to `challenge_from_parts` and in `import_state`.

## Secrets in `Debug`, headers, the local store

- Wire and binding records that carry a secret (TOTP setup, share passphrases and tokens, signup tickets, email codes, push tokens, recovery codes, passkey PRF output, …) print it redacted, and the ones a person types or copies (TOTP setup, share passphrases, recovery codes, PRF output) also keep it in `Zeroizing`: `beebeeb-api`'s `redacted_debug!(Type; show: [...]; hide: [...])`, UniFFI's `SecretString` / `SecretBytes` custom types (plain `String` / bytes in Swift and Kotlin). A new secret-bearing field joins `hide`; `tests/redaction.rs` asserts the redaction.
- `beebeeb-api` request `Debug` prints a header's value only when its name is in `DEBUG_VISIBLE_HEADERS`; everything else, `Authorization`, `Cookie` and `Set-Cookie` included, is `[REDACTED]`.
- `beebeeb-store` is a plaintext cache: decrypted names, MIME types, sizes, the tree, unauthenticated contact-key pins and the rollback high-water marks of `file_versions`; no key and no token. - `product_keys` derivations have known-answer vectors computed outside Rust (Python `hmac`), so a change to the derivation fails a test.

### Upload pipeline planner (task 2173 C1-C2)

`direct_transfer::upload_pipeline::PipelinePlan` is the pure per-file scheduler. The driver
starts with `Tick`, reads once for each `Accept`, and retains each chunk's exact ciphertext
until `CommitDone` or `GrantSkipped`. `GrantVersion` is fixed at init. Production drivers
use `with_seed` with fresh caller entropy; `new` is the deterministic seed-0 parity surface.
One grant/PUT lane overlaps two commit slots below 16 MiB, one from 16 MiB. Retries use the
unchanged `UploadChunkState`; holds keep their slot and their separate allowance. The first
grant 429 can await a process `Ack`, bounded by a separate 150 s accumulator. `Tick` advances
time and does not impersonate an ack. Grant/commit failure events carry the HTTP status
alongside the classified outcome, because only that preserves the specified 429/503 rules.

A `Wait(Gate)` is shared by the driver's grants/inits only. A commit 503 is a chunk wait,
a hold is a hold wait, and neither gates other work. On `GiveUp`, cancel PUTs and let commit
requests settle before the caller's recovery; `Producer` preserves the session and does not
arm a direct hold. Interrupt sends each already-staged commit once and does not poll holds.
`ReleaseLane` starts a tail of at most S chunks; if the last PUT stages behind S occupied
slots, the release waits for one ack to admit that commit (§3.4's tail memory bound).

The 66 scenarios / 423 event steps in `test-vectors/direct_upload_pipeline.json` run through
one `vectors::PipelineSurface` interpreter; each row names its contract source and asserts
actions, completion and (where relevant) retained counts. Generate with
`python3 test-vectors/tools/make_direct_upload_pipeline_vectors.py`. C3 adds binding surfaces
to the same interpreter with BV3, in one upload-exports PR. No bindings are regenerated by
C1-C2. `storage_put_total_shared` and `put_allowance` live in `timeouts`; clients copy neither
formula. This adds scheduling rules only: direct upload remains disabled by the server flag.

## L2 driver (`beebeeb-transfer`) — task 2173, plan K1/K2

`beebeeb-transfer` is the transport-independent driver above core's pure rules, shared by the CLI and desktop (and later bindings): one `download()` call takes any `DirectIo` implementation and performs the plan. It owns no rule — the planner, classifier, retry policy, timeouts and body counter all come from `beebeeb-core::direct_transfer`.

- `DirectIo` is the whole transport seam: `api` (adds the caller's `Authorization` and client headers), `storage_get`, `storage_put`, `sleep`, `wall_ms`, `mono_ms`. `StorageGet` takes a `SignedUrl` whose `Debug`/`Display` print only scheme and host, so a URL cannot reach a log or error through the driver.
- Storage GETs are bounded by `storage_get_total(ciphertext_len)`, idle for `STORAGE_GET_IDLE`, read at most `expected_len + 1` body bytes, and report `status: 0` for any transport error. API calls read at most `max_body` bytes and are bounded by their own `timeout`. The conformance suite checks that contract: no redirect is followed, no cookie is sent, no `Authorization`/`X-Beebeeb-*` header reaches storage, an idle body and an exceeded total both end as status 0, an overlong body is visible as one byte too many, the API body stops at `max_body`, and the API timeout bounds the call. The suite does NOT cover `check_storage_url`: a plain-http non-loopback link (for example `192.0.2.1`) is still refused by that core helper, which every transport calls before fetching a link.
- Every storage body is judged by `StorageBody::from_head` / `push` / `finish`; only `Stored` is `fetch_ok`, anything else is `fetch_failed`. The driver does no length comparison of its own.
- The pinned per-chunk route is `Call::PinnedChunk` with core `PinnedRetry::default()` (4 attempts, 150 s of waiting); its body read is bounded by `storage_get_total(len)`, not `API_CALL_TIMEOUT`.
- `DirectStore::global()` is a `OnceLock` keyed by `(api_base, account_id)`; entries share discovery cache and breaker health, and `forget_account` drops every entry of one account. `HealthSnapshot` stores wall-clock timestamps; the driver records breaker trips on `mono_ms` and converts at the boundary. One discovery call runs per entry: the leader holds a drop guard, so a cancelled or panicked discovery ends the flight as `Unavailable` without a cache write and wakes every follower instead of leaving them waiting for ever; a follower keeps one waker across repeated polls.
- Plaintext reaches the sink only after the chunk authenticates, in order; nothing is published on `FileChanged`, `Unauthorized`, `Forbidden` or `Unauthentic`, and a fallback returns `UseApi` with the reason. Pacing uses `paced_until_ms` over monotonic time. No event, error or `Debug` string carries a URL.
- The sink contract (plan amendment 2026-10-30): `PlaintextSink` has `write`, `discardable()` and `discard()`. "Written" is a dirty flag set BEFORE each write, so a write that fails partway counts. Every exit goes through `finish_attempt`, which applies one table: not dirty → the result as is; dirty and discardable → `discard()`, then the original `UseApi`/`Err` (a discard error never hides a 401 or 403); dirty and not discardable → `DownloadError::DirectFailedAfterWrite { written_plaintext_bytes, chunks_written, cause }`. `written_plaintext_bytes` counts the bytes handed to the sink, including a partial write, and its `Display` says "at least". A drop guard applies the discard row on cancel and records the storage breaker when the planner had given up storage. `TransferEvent::Discarded` means the bytes are gone; `TransferEvent::DiscardFailed` means they may remain and the outcome is unchanged. `UseApi` always means the sink holds nothing.
- Caller rules: (1) after `UseApi` or any `Err`, the API path or a retry always uses a FRESH sink; (2) never retry into a sink that returned `DirectFailedAfterWrite` — report an honest failure with a non-zero exit; (3) clients write to `<path>.bbtmp` and rename, never stdout straight to the driver; (4) each attempt's `.part` is unique (O_EXCL plus a random suffix) and `discard` works on the open handle only, never by path; (5) clients delete stale `.part`/`.bbtmp` files at startup (`panic = "abort"` and a kill skip every guard).

## Backups (`backup/`, `beebeeb-backup`) — LD-0113

The backup rules every client shares (spec `2026-11-06-backup-from-source-design.md` §4; plan Amendment 1, lead 2026-11-06). L1 is `beebeeb_core::backup` (pure) and `beebeeb_types::backup` (wire strings); L2 is `beebeeb-backup`, the filesystem pass for desktop and the CLI over a `BackupHost` the client implements. iOS reads PhotoKit, not files, and uses L1 through uniffi.

- **The root is the row with `system_role = "backups_root"`, never a path or a name.** It is named `Backups` (`ROOT_NAME`), and every client shows the badge `MSG_BADGE` ("Read-only") on it; the read-only state is never put in the name (Guus, 2026-11-06 20:04: "keep it Backups and just add a read-only badge"). The root's words (`MSG_DELETE` and `MSG_MOVE` are iOS's strings byte-for-byte) are the server's too: it answers `409 protected_folder` with them. `resolve_root` claims the oldest live `Backups` for an account from before the flag (ties by id; a pending name never counts), so clients migrating at once converge; `plan_merge` folds the duplicates in (keep-both on a clash; pass `hhmm` with a dot, never a colon).
- **A backup is written by its device's own backup and by nothing else** (spec Amendments 7 and 8, Guus 19:30, 19:33 "Both, staged"; the manifest position, lead 20:01). `BackupPosition` is a row's place (`at_depth(depth, name)`: none outside, 0 the root, 1 a device folder, 2 the device's `Manifest` when the name is exactly `.device.json` and else a category folder, 3 or more inside; lead 20:01); `is_hidden_backup_item` is `true` for the manifest only, and clients never list it; `Mutation` adds `Create` (checked on the destination folder: an upload, a new folder, a move's destination; a move checks its row with `Move`) and `Write` (a content change or a new version). Three rules, one set of words: `check_app_mutation` (web, desktop in the app, iOS, the CLI): the root refuses everything, and so does a device's manifest (`MSG_READ_ONLY`; trashing it alone would make the device create a second folder); under the root only trash and delete are allowed (the device-folder dialog, one file deleted from a backup), everything else is `MSG_READ_ONLY`. `check_drive_mutation` (Explorer, Finder, the Files app): nothing at or under the root changes; the root's own words first, then `own_backup_refusal(path)` for this device's own backup of a folder still being backed up, then `MSG_MANAGED_IN_APP` (structural) or `MSG_READ_ONLY` (create, write, and anything on the manifest). `check_root_mutation` is the server's phase-1 rule: the root's trash, delete, rename and move only (`409 protected_folder`, same words). The backup pass never goes through any of them; every request a host makes for a pass carries `X-Beebeeb-Origin: backup` (`ORIGIN_HEADER`, `ORIGIN_BACKUP`), which the server will use in phase 2 to refuse an untagged write in the tree. The root shows the badge `MSG_BADGE` ("Read-only"). `Protected.message` is a `Cow<'static, str>` so the own-backup words fit.
- **Device ids are string identities** (a UUID, or an iOS legacy `beebeeb_device_id` value carried forward verbatim); `same_device_id` compares UUIDs as UUIDs, anything else exactly. A legacy id's collision suffix is the hex of its bytes. A candidate whose manifest does not parse is `FolderManifest::Unreadable`: not mine, never adopted, its name taken, and it never fails the choice.
- **Custom folders** are named once, when added, by `custom_category_name` (the device-folder safe-name rule, then ` (2)`, ` (3)` against the fixed categories and the device's other custom folders, folded; at most 200 UTF-8 bytes with the suffix and a reserved stem's `_`: the base is cut, never the suffix, so two long names never share a folder; `clean_name` is idempotent, review 4 #4); the server folder is `category_folder_name`, never the raw `display_name`.
- **Keys** are NFC on macOS (APFS and HFS+ cannot hold names that differ only in normalisation) and the raw name on Linux and Windows (spec Amendment 5, lead 17:34): a key never moves from one file to another. Pairing is exact first, then `normalize_key` among what is still unpaired, so a lone NFD record never pairs with a newly appeared NFC twin.
- **Device folders:** `find_device_folder` picks the manifest with my id, else (desktop only) a manifest-less folder with my exact name (the old mirror's `Backups/GLegion`), else a new folder named by `device_folder_name` with a ` (xxxx)` id suffix on a collision with another device. The desktop id is `device_id_from_machine_id` (SHA-256 domain label `beebeeb/backup-device-id/v1`, in `label_table_tests.rs`); the raw machine id never leaves the device and the derived id lives only in the encrypted manifest.
- **The manifest** parses tolerantly: unknown fields are kept and written back, a `folders` entry's own included (`FolderState::other`); a `device_id` that is not a string or an unknown `platform` parses as `None` with its text kept verbatim. Only a document that is not a JSON object is unreadable (delta 3 #7): a null or wrong-typed `version` / `device_name` takes its default, `folders` that is not a list is empty, and each `folders` entry is read alone (a missing or null field takes its default; an entry that still does not fit is dropped alone), so one bad entry never hides the device id and never makes the device create a suffixed folder. On write a known field always wins over kept text of the same name (a renamed device keeps its new name). Parse errors never quote the document (it holds a device name).
- **Never backed up:** OS junk, macOS library bundles (folders only), links (std's `is_symlink()`: symlinks and junctions, by the reparse tag's name-surrogate bit), and entries whose bytes are not on this device (Windows recall/offline bits, macOS `SF_DATALESS`, `.icloud` stubs by name in `skip_reason`). The raw `FILE_ATTRIBUTE_REPARSE_POINT` bit is never a link: OneDrive sets it on every file, local ones included, and a local OneDrive file is backed up (plan Amendment 1, item 7). A not-local folder is never descended into: listing it would fetch it. Name rules come first, then not-local before link, so a OneDrive cloud placeholder counts as online-only.
- **The walk** reads attributes from the directory listing only (`DirEntry::metadata`; on Windows the `FindNextFileW` data, no handle), never `fs::metadata` on an entry's path before its not-local check (item 9). The backed-up folder itself is read the same way, from its entry in its parent's listing (each hop of a linked root likewise; a traverse-only parent gives the hop's own metadata, not followed): a root that says not local is one `NotLocal` skip at key `""`, never listed (delta 3 #4); a root whose path holds `..` is `InvalidInput` before anything is read (`absolute` keeps `..` on Unix, and such a root has no entry of its own; review 4 #5). It never enters an `exclude` path, reported as `Excluded` (item 8): desktop passes its sync root, the CLI its sync folders, or the drive would be backed up into its own Backups. An empty, relative or `..` exclude path is an `InvalidInput` error (empty would cover everything); the paths are folded once before the walk, with core's `fold_name` on Windows and macOS, and compared as given and as resolved (links followed) against the root as given and as resolved, so a linked root still meets a sync root spelled through its target (delta 3 #5). A source root inside the sync root is refused by desktop (D4), not core. A folder is listed whole or reported `Unreadable`; a failure partway through the backed-up folder itself stops the pass.
- **The planner** pairs records with entries on the exact key, then on `normalize_key` (NFC, `\` → `/`). A move needs a gone, live, backed-up record and a new entry with the same size, mtime and case-folded name, unique both ways (a case-only rename is a move). A record whose server copy is missing from a COMPLETE listing (`live_remote_complete`, `DeviceTree::complete`) becomes `RemovedElsewhere`; from an INCOMPLETE listing it is unknown (lead 17:28): no upload for its file, no move from it, no mark, counted in `deferred_unknown`; a new entry whose signature an unknown record shares waits too, even when a live record has it (review 4 #6). The first upload always fits: `max_uploads` 0 counts as 1 (review 4 #7). Each record to mark removed elsewhere is a `RecordRef` (key and remote id): the host marks it only while the record at that key still names that remote id and is `BackedUp` (compare-and-set, review 4 #3). After a move, `put_record` re-keys the record the pass read and keeps its stored fields (an upload of a new version may have finished meanwhile); when an upload replaced the old key's record with another remote file, it stores the moved record, so the moved file keeps one; when another key's record names the file by now, it does nothing and the move counts as deferred (delta-4 self-review). Held keys (`BackupHost::held_keys`: a lasting failure, or in flight) are skipped and charged nothing, so one stuck file never starves the rest. Every upload carries the paired `record_key`, and a `Changed` one the `remote_id` it versions; the host re-keys the record, never looks it up by the entry key. It uploads again only when the file changes, and then as `New`, never as a version of the deleted copy (ruling A); the client writes a fresh record when that upload completes. A record whose copy is live again (restored from Trash) is held again: unchanged, and a move source. Records at or under a key the walk did not look into (`WalkResult::unseen`; `""` = the whole folder) are left untouched: never gone, never a move source. A record matches raw, or, when no entry has its exact key, by its folded key (`fold_name` of the normalised key: NFC and case; exact-then-normalised, Amendment 5; delta 3 #3, review 4 #2), so a legacy NFD record under an unseen NFC folder, or a record under an unseen folder renamed only in case, is covered too; the fold applies on every platform (on Linux a case twin's record waits, the safe side). A file entry under an unseen raw key is not planned; entries match raw only, so an unreadable NFD folder never hides its NFC twin. The budget keeps a prefix and the first upload always fits. `records_from_remote` matches the exact key first, then the normalised key only when one entry has it. A key's every `/` is a folder boundary: iOS passes asset ids with `/` replaced by `|`.
- **Rebuilding records** (LD-0123): `records_from_remote_with_clock(remote, entries, clock)` marks an entry backed up only when a copy with its key and size was uploaded after `modified_ms + offset + margin` (`RebuildClock::copy_is_newer`, exact in i128). `uploaded_at_ms` is the server's clock and `modified_ms` the device's: a clock that runs behind would otherwise make a same-size edit look older than the copy and it would never be uploaded. `rebuild_clock_from_date(date_header, sent_at_ms, received_at_ms)` measures the offset (`server_now - device_now`) from a listing response's `Date` against the request's midpoint, margin `REBUILD_MARGIN_BASE_MS` (2 s: the header's whole seconds) plus the round trip; no header, one that does not parse, or a negative round trip gives `RebuildClock::UNKNOWN`. With no offset known the offset is 0 and the margin is at least `REBUILD_FLOOR_MS` (10 minutes, one-sided: a clock further behind is covered only by a measured offset). The floor costs every device, a correct clock included: a copy made within 10 minutes of its file's last change (an auto-backup usually is) is uploaded again, so clients measure an offset whenever they list. `records_from_remote(remote, entries)` keeps the v0.2.1 signature and applies `UNKNOWN`; desktop's rebuild calls it today and must move to the clocked call. The offset is measured now, not when each mtime was stamped: a clock that was behind then and has been corrected since is not covered (decision LD-0122, a sealed mtime, would be). The margin assumes the server nodes agree within the slack second. Every error leans toward uploading again.
- **Why a backup stops** (spec Amendments 12, 12a and 12b, LD-0121; Guus: "Stop, say why, offer Back up again"): `backup_stop(notices, last_pass_at_ms, listing)`. Notices are the server's `notifications` rows (`BackupNotice` in `beebeeb-types`: `files_removed {reason}`, `backup_deleted {device_folder_id, category_folder_id?}`, ids only), read leniently with `parse_backup_notice` (another type is skipped; a removal whose reason this build does not recognise, or none, still stops every backup, as `UnknownRemoval` with its own line "Your files were removed, so backups are off." (Amendment 12b), never the `Unknown` row's "deleted" words; a malformed id names no folder, never the device). The wasm `backupStop` skips any row that is not a backup notice whatever its shape, and throws on a backup notice without a whole `created_at_ms`. Only notices with `created_at_ms > last_pass_at_ms` count, and `last_pass_at_ms` is on the SERVER's clock (the previous pass's start, or the moment the person turned the backup on or chose "Back up again" since): a device clock that runs ahead would hide a notice and the pass would fill the account up again. 1. the newest `files_removed` notice turns every listed backup off with its reason, folders present or not; 2. per backup, a `backup_deleted` notice naming this device's folder, with no category id or with its category folder: `BackupDeleted` (a notice with another device's folder id counts for nothing; a gone folder still stops at step 3); 3. a device or category folder trashed or gone with no notice: `Unknown`; 4. nothing. Steps 2 and 3 are per backup. A notice wins over a restore from Trash (the accepted edge); with no notice a restore changes nothing. The words: `backup_stop_words(reason, device, folder)` and `MSG_BACK_UP_AGAIN`; Amendment 12's six lines are final as drafted, plus 12b's seventh (Guus 2026-11-07 19:04, G6). Bindings: uniffi `backup_stop`, `backup_notice_reason`, `backup_stop_words`, `backup_again_action`; wasm `backupStop`, `backupNoticeReason`, `backupStopWords`, `backupAgainAction`.
- **`run_pass`** reads records BEFORE the device tree (a finishing upload's record is then always in the listing), turns the backup off when the device or category folder was deleted elsewhere, and never writes an upload's record: the client does when the upload completes. Before planning it reads again from the file each entry whose listing differs from its record (Windows directory entries can be stale; the record holds the handle's values), so a stale entry never takes the budget (delta 3 #6). It checks what can fail (the category folder's id, every move's record, every upload's path) before its first change to the host's store or the server (delta 3 #8). On Windows and macOS a planned folder whose key folds equal (`fold_name`) to an existing server folder is that folder, so a case-only or NFC/NFD-only rename creates no sibling, and a file already where its move puts it is only re-keyed (delta 3 #2). After a move it calls `put_record`, which keeps one key per remote file. It reads the records again just before it enqueues and drops an upload whose key a finished upload has recorded meanwhile; `enqueue_upload` drops one that slips past (host obligation). Right before the handoff it re-reads each file's metadata: a file gone online-only is held back as `NotLocal`, one it cannot read as `Unreadable` (both in `PassReport::held_back`, by key), one that vanished is counted in `vanished`; the uploader (desktop D3) still never reads a placeholder whose recall bit is set. A `Changed` upload is a new version of the record's remote file, never a second file. The source is the person's file: it is read in place, never staged, moved, deleted or given new attributes; the uploader compares `Fingerprint` before the first chunk and after the last and abandons the session on any change.
- **Logs and errors carry counts and kinds, never a name, a path or a device name.**

## Range reads (`RangeOpener`, `RangePlanner`, `RangeSession` = `range_session`) — LD-0105

A range session serves reads at any offset while the download runs (desktop Windows hydration first; later the iOS loopback server and Linux FUSE), releasing each chunk as soon as it authenticates instead of after the whole file. It is the one exception to the whole-file `finish()` rule. Names in code: `chunk_stream::RangeOpener` (opens frames), `direct_transfer::range::RangePlanner` (what to grant and fetch), `beebeeb_transfer::range_session` (the session; the contract's `RangeSession`), whose only "whole" result is `range_session` → `RangeOutcome::Whole` (the contract's `RangeSession::finish()`): it is returned only when `RangeOpener::finish()` passed for this attempt (every index opened), every byte of the file reached the sink and the piece cutter holds nothing. With ONDISK = 0 an old recorded identity is ignored (spec S3: nothing to trust).

**Invariants I1–I9** (binding on every range reader and on each client's glue):
- **I1.** The release unit is one whole AEAD frame, opened by core at the requested index. No byte is released before its tag.
- **I2.** Position comes from the request: `is_last = (index == n−1)` from the session's one geometry; offset = `index × chunk_size`; decrypted length = `chunk_length(index) − 28`; `original_size` = the size the OS holds for the file (the placeholder's `FileSize`); on any mismatch, nothing is transferred.
- **I3.** Identity is fixed once per session. The format comes from the pin (`decrypt_file_metadata[_with_key]`). Frame 0 opens first: it decides an unrecorded file's format and carries a v2 file's version id. When the same metadata carries a version commitment (`RangeRequest::version`), frame 0 opens only as that v2 upload, as in the whole-file read, and a stride from authenticated metadata (`RangeRequest::authenticated_chunk_size`) must match the session's geometry.
- **I4.** One sink (placeholder) holds one attempt of one version. The identity `(object_version_id, format, v2 version_id)` is recorded before the first transfer; no record while the sink holds bytes is a mismatch. A mismatching session fails, and the sink is poisoned and emptied; it never writes into a foreign sink. Any failure after a transfer is `DirectFailedAfterWrite`.
- **I5.** A failed sink is poisoned until it is verifiably empty: no fetch for it (0 GETs), the poison survives a restart, and the client's empty step runs outside any callback. (Windows: one exclusive `CfOpenFileWithOplock` handle; unpin → IN_SYNC → dehydrate → ONDISK = 0; on any failure NOT_IN_SYNC and the pin are restored before the handle is released.)
- **I6.** "Whole" is the session's finish verdict: every index `0..n−1` opened and transferred in this attempt, and v2's last frame opened as last. It is the only path to in-sync, agreed content or "complete". A file completed across two sessions is never whole.
- **I7.** A failed demand gets a non-success status on its remaining range, never zeros or a short transfer.
- **I8.** Plaintext is `Zeroizing`: at most one chunk per transfer (plus the piece cutter's partial 4 KiB blocks), wiped after the hand-over. No temp file, no name or URL in logs.
- **I9.** The record is honest: **v1 frames carry no position, version or truncation binding.** New files are written as v2 (`WRITE_FORMAT = V2`), but legacy files stay v1, so a server or storage attacker can reorder or duplicate equal-length frames, truncate at a chunk boundary, or splice another version of the same file id, and `finish()` for v1 checks only that every index opened (the geometry is the server's statement). Also, under an `Unrecorded` pin a no-AAD blob sealed under the raw file key (an old name or thumbnail envelope) can be served as frame 0 and opens as v1, the same detection `ChunkDecryptor` does. This is the same gap the whole-file read has: streaming changes when bytes arrive, not what can arrive. The v2 guarantees (index, `is_last`, version, file bound in the AAD; truncation caught at the last chunk) apply only to v2-pinned files. Test T5 pins the v1 gap.

**Tests that hold them** (each seen red on its named mutant, task LD-0105): `chunk_stream::range::tests` T1 (index/duplicate/version/file binding; mutant: the index from the server), T2 (geometry one short / one long; mutant: `is_last` not bound from the geometry), T3 (an unrecorded v2 file with a raw-key frame; mutant: per-chunk detection), T4 (a length the geometry does not allow, v1 and v2; mutant: no length check), T5 (v1 swap, characterisation); `beebeeb-transfer` `range_tests` T6 (a tag flip at chunk k leaves exactly 0..k−1; mutant: release before open), T7 (no restart into a written sink; mutant: a failure after a write reported as nothing written), T8 (identity mismatch transfers nothing, a match resumes; mutant: the identity check skipped). T9–T11 are the desktop's.

**`RangePlanner`** (`direct_transfer/range.rs`): a new type, not built on `DownloadPlanner` (whose "Client wrapper rules" stay binding for it, `window.rs`). It holds a set of released chunks, asks for windows at any start, with grants only for the next window-size of wanted chunks, and every window carries the pin. Order: chunk 0 first (I3), the demanded chunks (oldest demand first), then read-ahead: the last chunk, forward from the furthest demand, then the gaps from the start, until whole. No later chunk starts before chunk 0 has, and chunk 0 keeps its slot and its booking until it is released, so its refetch never waits for room held by the frames that wait for it, even after the share shrank (`poll_with(.., may_fetch = false)` still starts it; the caller keeps chunk 0's booking, or calls `bookings_returned` when it gives its lease back with nothing held). Read-ahead stops on a cancel with no demand left and when the requester is gone. An idle grant ages out without spending the renewal budget and is granted again only for a demanded chunk, at most once per demand; a re-grant that ages out again spends renewals (so it ends on the pinned API route, never in a loop), and a paused session with only read-ahead asks for nothing. It composes `DownloadPlanner`'s checks through `direct_transfer/grant_check.rs` (one `check_window`: transport, file, pin, geometry, grants, method, length, `check_storage_url`, expiry inside the skew margin; one renewal rule, one 429 rule, one backoff), and a parity suite replays `direct_transfer.json`'s 21 refusal rows and 59 authority rows against it (red on a mutant that skips `check_storage_url`). Its unauthentic handler: a range session has released only frames `RangeOpener` authenticated; on that verdict it poisons the sink (I5) and releases nothing more.

**Range-read amendment to the direct-transfer client rules** (honesty trigger 2, recorded): for a range session, chunks are released in any order, each only once `RangeOpener` authenticated it at the requested index; the reorder bound is the byte share below, not a consumed prefix; "Publish plaintext only after every chunk has authenticated" reads "release a chunk only after it authenticated, and call nothing whole before the session's finish verdict".

**The in-flight split (C3) and the budget (S8):** `storage_in_flight = clamp(floor(share / (chunk + 28)), 1, 16)` (16 / 16 / 15 / 7 / 3 / 1 slots for 4–128 MiB chunks on the native 256 MiB); pinned API fetches inside a session ≤ `API_IN_FLIGHT` = 4 (the plain per-chunk API route outside a session stays at 1, desktop); window = `min(server max_window, max(8, N + 2))`. `DownloadPlanner` keeps its numbers (4 in flight, window 8) for every existing caller. `RangeBudget` is the process book: at most `MAX_SESSION_LEASES` = 4 sessions hold a lease (a fifth waits; an idle session gives its lease back, one short of room keeps it and waits for the lessor's wake); a fetch is booked before it starts when `held + len <= max(share, len)` and `total + len <= max(budget, leased × len)`, so the ciphertext held never exceeds `max(256 MiB, leased × (chunk + 28))`. `beebeeb_transfer::RangeLessor` wraps it (one per process, `RangeLessor::global()`).

**Pieces:** `PieceCutter` cuts released plaintext so every piece starts on a 4 KiB boundary and is a multiple of 4 KiB unless it ends on EoF (Cloud Files TRANSFER_DATA), for any chunk size (1 MiB, 1,000,000 bytes) and any release order, carrying unaligned heads and tails in `Zeroizing` 4 KiB blocks. `demand_chunks` widens a demand to whole pieces, so a demand never waits on a piece the next chunk completes unless that chunk is demanded too.

**Vectors:** `test-vectors/direct_range.json` (slots, window, demand → chunks, pieces, budget incl. 10 sessions × 32 MiB → at most 4 leased and ≤ 256 MiB held, planner scenarios: a seek with chunk 0 first, a cancel, the idle re-grant rule), generated by `test-vectors/tools/make_direct_range_vectors.py` (an independent implementation of the spec text; scenario rows hand-written from it) and guarded by `check-direct-range-vectors-generated.sh` (`--self-test` proves it goes red; both run in CI). The interpreter `direct_transfer::range::vectors` asserts the per-section row counts.

**What a client's glue must still do** (desktop W2): pass the minted version and the recorded identity and ONDISK into `RangeRequest`; persist the identity `record_identity` hands over before acknowledging it; on `DirectFailedAfterWrite` or `IdentityMismatch`, poison the placeholder and run the empty step (I5) before any session may write; answer `demand_failed` with a `STATUS_CLOUD_FILE_*` status (I7); mark in-sync / agreed content only on `RangeOutcome::Whole` (I6); never log a name or URL.

**Decision (core lane, 2026-11-05): ranges live in `beebeeb-transfer`, the whole-file download stays where it is.** The modular split (§16.2 row 10) names `beebeeb-upload::download` as the owner of the download move, but the L2 driver that exists for direct transfers is `beebeeb-transfer`, and the range session needs its `DirectIo` seam, discovery cache and pinned-route policy. So `range_session` and `RangeLessor` go in `beebeeb-transfer`, and the whole-file `beebeeb-upload::download` keeps row 10.

## Archives (`archives/`)

List, preview and extract zip, tar, tgz and gz (`2026-11-07-core-archives-design.md`). `ArchiveSession` is
sans-I/O over a `ByteSource`: native sources block (`ReadSeekSource`); push drivers (web) answer
`NeedBytes` through `SuppliedBytes`, at most `MAX_SUPPLIED_BYTES`, and every step is atomic, so a miss is
retried, never half-applied. Detection is by magic bytes, never the extension. Zip entries are decoded by
core's own push pipeline (raw inflate, CRC-32, WinZip AES on `aes`/`hmac`/`sha1`, ZipCrypto) because zip 9's
readers borrow the archive and collapse duplicate names; zip 9 is the writer and the tests' reference
reader. Names go through `archives::names` (design §6.1); the planner numbers clashes with
`name_clash::numbered_name`; `Extraction` hands a file over (`FileEnd`) only after it verified, and binds
the run to one archive version. The preview model and every word (`ArchiveText`, 63 keys) are core's.
Vectors: `test-vectors/archives_v1.json` and the fixtures in `test-vectors/archives/`, written by
`gen_archives_v1.py` (no zlib: deflate is one fixed-Huffman block) and guarded byte for byte by
`check-archives-vectors-generated.sh`; the password fixtures come from 7-Zip and Info-ZIP. Bindings:
`WasmArchiveSession` / `WasmArchiveExtraction` (`archives.test.cjs` runs every vector row) and the UniFFI
records in `beebeeb-uniffi/src/archives.rs`.

## Security invariants

- MasterKey and FileKey are NOT Clone — prevents accidental key copies in memory
- All intermediate key buffers use `Zeroizing<[u8; 32]>` — zeroed on drop
- Each file gets its own key via HKDF(master_key, file_id) — limits blast radius
- Recovery phrase IS the master secret — password wraps it, doesn't replace it
- No panics in crypto paths — everything returns Result

## Link labels, guest actor names, the legacy child opener (L16, task 2275)

- **Link labels:** `kdf::wrap_link_label` / `unwrap_link_label` bind a UTF-8 label to the owner's master key with HKDF-SHA256(ikm = master, no salt, info = `beebeeb-link-label-v1` || the 16-byte share id) and that same context as AES-GCM AAD, exactly like the L6 owner wraps. Writer and opener normalize to NFC (the opener never refuses non-NFC plaintext) and enforce 1..40 Unicode scalar values after NFC.
- **Guest actor names:** `kdf::seal_folder_actor_name` / `open_folder_actor_name` derive HKDF-SHA256(ikm = folder key, info = `beebeeb-folder-actor-name-v1` || the 16-byte shared root id) with the same AAD. Both sides apply ONE rule, `kdf::sanitize_actor_name`, and the writer seals its result, so core never seals a name its own opener refuses: NFC; strip every `Cc` character and the explicit table (U+00AD, U+061C, U+180E, U+200B, U+200E, U+200F, U+2028-U+202E, U+2060-U+2064, U+2066-U+206F, U+FEFF, U+FFF9-U+FFFB); NFC again; refuse a leading combining mark; 1..64 scalars after that; refuse a visibly blank name (only whitespace and the invisible-filler table, which covers every Default_Ignorable_Code_Point that is not stripped). ZWNJ, ZWJ, variation selectors and tag characters are KEPT (Persian/Indic spelling, emoji ZWJ sequences, subdivision flags). Writer refusals are `InvalidInput`; opener refusals are `Decryption`.
- **Envelope:** a JSON object with exactly the keys `cipher_suite` (the string `V1Aes256Gcm`), `nonce` (12 bytes) and `ciphertext`: all required, none `null`, no other or repeated key, no JSON array form. Key order and whitespace are free, so a hop that re-encodes the JSON (JSONB, `JSONEncoder`, pretty-printing) stays openable.
- **Strictness:** an id that is not exactly 16 bytes is `InvalidInput`; a swapped share/root id, another purpose string in the info or the AAD, another container, invalid UTF-8 or a plaintext the rules refuse is unopenable. There is no second key and no second shape.
- **The legacy child opener:** `kdf::open_legacy_child_key` opens only a 60-byte unbound frame (nonce || ciphertext || tag, empty AAD) under the folder key, and refuses a 32-byte plaintext that is valid UTF-8 (L9 rule 1), so a name or label sealed under the same folder key can never be served as a child key. There is no legacy reader for the pre-L16 label or actor-name formats.
- **Bindings:** WASM `wrapLinkLabel`, `unwrapLinkLabel`, `sealFolderActorName`, `openFolderActorName` and `openLegacyChildKey` (ids are UUID strings, keys are bytes as in L7); UniFFI `MasterKeyHandle::wrap_link_label` / `unwrap_link_label` and `FileKeyHandle::seal_folder_actor_name` / `open_folder_actor_name` / `open_legacy_child_key`. No raw key bytes cross the UniFFI boundary.
- **Label table:** `src/label_table_tests.rs` lists every HKDF info / AAD / salt label in the crate with its slot, requires them distinct, refuses an id-carrying HKDF info that prefixes another HKDF info, documents the three cross-slot prefix pairs (`beebeeb/chunk/v2` / `.../key`, `beebeeb/client-meta/v1` / `.../key`, the `beebeeb-share` salt / `beebeeb-shared-folder-index-v1`), and scans `src/` so a new `b"beebeeb…"` label cannot be added without joining the table.
- **Vectors:** version 16 carries `link_label_v1`, `folder_actor_name_v1` and `legacy_child_refusal_v1` (15 is unused: an earlier draft on the unmerged branch); the core drift guard regenerates them, and `beebeeb-wasm/js-tests/l16_labels.test.cjs` opens them through the WASM exports.
