## Corrected L9 (Claude lane w2255, 2026-10-28)

This replaces the per-row verifier above. It follows the lead's "L9 correction" in the task file (workspace #236). The crypto-security review of 66b32a3 found P1-1: attack A passes the old proof. The old fix still closed the original server-only name-blob attack.

Core API (`beebeeb-core/src/kdf.rs`):
- `verify_legacy_folder_key(master, candidate, rows) -> bool`:
  1. a candidate that is valid UTF-8 is refused;
  2. some row `(file_id, wrap)` must open under the candidate (legacy, empty AAD) to exactly `derive_file_key(master, file_id)`. ANY row counts, including the folder's own row. Each `file_id` is examined once, and at most `LEGACY_FOLDER_KEY_PROOF_CAP` = 64 distinct ids are examined;
  3. the comparison uses `subtle::ConstantTimeEq`.
- `open_legacy_invite_owner_copy(master, folder_id, legacy_copy, rows) -> Option<FileKey>`: opens the legacy copy under `derive_file_key(master, folder_id)`, requires 32 bytes, then runs the proof, in ONE call. The unproven candidate never leaves core.
- Exports: WASM `openLegacyInviteOwnerCopy(master, folderId, legacyCopy, rows)`. `rows` are the server's `GET /shares/invites/{id}/folder-keys` rows verbatim, read lazily, and the call returns `undefined` when there is no proof. UniFFI `MasterKeyHandle::open_legacy_invite_owner_copy(folder_id, legacy_copy, Vec<LegacyFolderKeyRow>) -> Option<FileKeyHandle>`. The per-row `verifyLegacyFolderKey` / `verify_legacy_folder_key` exports are removed. They were never pushed.
- Purpose-bound owner copies (`wrap_/unwrap_invite_owner_copy`, `beebeeb-invite-owner-copy-v1`) are unchanged.
- New direct deps: `subtle = "2.6"` (core) and `base64 = "0.22"` (wasm). Both were already in Cargo.lock, so the lock gains two dependency edges and no new packages.

Named residuals (NOT fixed here):
- **Attack B:** a server that knows the folder's own name key `derive_file_key(master, folder_id)` (from a pre-2238 folder link, or a colluding member of an enclosing shared folder) can seal a non-text key of its choice as a legacy owner copy, plus a matching row, and the proof passes. The test `invite_legacy_residual_attack_b_name_key_holder_can_forge` pins this: it asserts the forgery IS accepted today, so the follow-up fix must flip it. Candidate full fix, per the lead: a proof from an approved member's X25519 recipient wrap, which the owner can reopen only if invite wraps are static-static. Investigate before the shared-folders flag flip.
- **P3-3:** neither owner-copy format binds a key version, so a server can present an older genuine owner copy and it passes.
- **Constant-time is checked by reading the code, not by a test.** Mutating `ct_eq` to `==` keeps all tests green (M4 below). `from_utf8` on the candidate exits early. Its timing can hint where the first non-UTF-8 byte of a real key sits, a few bits at most, to a local observer only.
- **Availability:** the server can always make the proof fail, for example by putting 64 non-proving rows first or by sending no rows. The caller then refuses (FOLDER_KEY_UNVERIFIED) and never mints a split key. A legacy folder with no owner-written row at all (an empty folder) can't be proven. That is a refusal, not a leak.
- **L7-bound rows are not legacy proof.** A custody folder never reaches this reader (L7b).
